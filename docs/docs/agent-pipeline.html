Architecture: the agent pipeline

How the pipeline that ships in every scaffolded suite (.claude/) is put together, and why. If you just want to use it, Getting started is enough — this is for understanding and extending it.

Design principles

● Never touch prod on the way Agents work only inside an ephemeral .agent-sessions/<id>/ copy; tests/ changes land only via an explicit promotion step.
● Human gate at the end Nothing merges without you running agent:promote after review.
● Reuse before writing The orchestrator regenerates + reads the step wiki first, so new work reuses existing steps.
● One tool touches the browser Only the bdd-explorer drives the playwright-test MCP; everyone else delegates.
● Adversarial review A separate bdd-auditor challenges assertion strength and coverage before promotion.
● Update agents in one place Agent definitions live in the package and are pulled per-project via playgentic sync.

Components

Three actors inside Claude Code, working against your repo and one real browser:

  • Orchestrator — the /bdd-pipeline skill. Reads the flag (--gen/--heal), plans cases, regenerates the wiki for reuse, scaffolds an isolated session, and dispatches the subagents.
  • bdd-explorer (sonnet) — the only actor allowed to launch the browser via the playwright-test MCP. It fills in PENDING step stubs by exploring the live app.
  • bdd-auditor (haiku) — an adversarial reviewer that challenges assertion strength and coverage against your standards in .claude/rules/code-styles.md.

The generation loop

/bdd-pipeline --gen adds coverage. The orchestrator plans and scaffolds; the explorer does all live-browser work; the auditor reviews; you approve.

  1. Guard the branch, plan cases, npm run wiki to surface reusable steps.
  2. agent:new — copy baseTest and extend files into a fresh session.
  3. Write the .feature and step stubs that throw PENDING.
  4. Dispatch the explorer with the session + test ids.
  5. The explorer loops (up to 3 repeats) until green: run → hit PENDING → explore the live app → fill the step → rerun.
  6. The auditor reviews changed files and reports BLOCK / MEETS / SHIP.
  7. You approve → agent:promote copies the session's tests/ over prod and regenerates the wiki.

The explorer's stub loop

New steps are scaffolded as stubs that throw. The thrown PENDING exploration is the explorer's signal to go look at the real app — it never guesses locators from stale artifacts; every exploration is fresh.

RunTest → hits PENDING / failure → Explore (snapshot, locate, infer on live app)
        → Patch the step → rerun → passes ✓   (or 3 fails → write FAIL_REASON.md)

The healing loop

/bdd-pipeline --heal repairs broken or flaky tests. Same isolation, but it starts from an existing failure and its priority is not weakening the assertion to make it pass.

failing test + report
  → agent:new --extend (copy the failing feature + steps)
  → reproduce in the session
  → bdd-explorer re-explores the live app and repairs
  → bdd-auditor guards assertion strength
  → approve? → agent:promote → tests/   |   no → back to the explorer

Runner isolation

The agents run through a dedicated Playwright project, agent-session, that is only defined when AGENT_SESSION is set and globs only that session's folder. Your real desktop/mobile projects and CI never see it, and it can never resolve a file under prod tests/.

agent:promote is the only bridge from a session back to tests/: it lints the session's docstrings, copies its tests/** over prod (extending existing files, adding new ones), regenerates the wiki, and typechecks — aborting before it writes if anything fails.

Keeping agents current: the sync model

Agent definitions are versioned in the playgentic package and pulled into each project. Files split into two buckets so updates never fight your customizations:

  • Managed — skills and agents. sync overwrites these to the shipped version.
  • Yours — rules/code-styles.md (copied only if absent) and any skill/agent you add. sync never touches them.
Editing a managed file forks it The next sync will overwrite a managed skill/agent you edited — by design. Put your standards in rules/code-styles.md (which the auditor reads) or add your own skills/agents, which sync leaves alone.

Extending the pipeline

  • Auditor standards — .claude/rules/code-styles.md is where most of the auditor's judgement comes from. The more concrete it is, the sharper the reviews.
  • Add a subagent/skill — drop it in .claude/; sync leaves anything you add alone.
  • Change the runner — the agent-session project in playwright.config.ts is a normal Playwright project; adjust its device/globs as needed.
