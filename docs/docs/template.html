Working off the template

A scaffolded suite is a normal Playwright-BDD project — you own every file. This page covers the layout, how to add a feature and step by hand, the docstring convention the wiki and lint gate depend on, the Playwright config, and how credentials flow in from the environment.

Project layout

my-suite/
  tests/
    baseTest.ts               # BDD binding + scenario-scoped `world` fixture
    features/*.feature        # Gherkin scenarios
    steps/*.steps.ts          # step definitions (each needs a docstring)
  scripts/                    # zero-dep tooling: wiki, step lint, agent sessions
  docs/                       # generated step wiki (npm run wiki)
  .claude/                    # agent skills, subagents, rules (managed by playgentic)
  .agent-sessions/            # ephemeral agent workspaces (gitignored)
  playwright.config.ts        # projects, reporters, the agent-only runner
  .env                        # TARGET_URL + optional creds (gitignored)

Adding a feature and step

Write a Gherkin scenario under tests/features/. Tag it for the project(s) it should run in (@desktop, @mobile), and reuse existing steps where you can:

# tests/features/search.feature
Feature: Product search

@desktop @search
Scenario: A query returns results
  Given I navigate to path "/"
  When I search for "widgets"
  Then I see at least 1 result

Then define any new steps under tests/steps/. Every step must carry a docstring (see below) — the pre-commit gate rejects steps without one.

// tests/steps/search.steps.ts
import { When, expect } from "../baseTest";

/**
 * @domain search
 * @description enters a query into the site search box and submits
 * @prereq on a page with the global search field
 * @uses page
 */
When("I search for {string}", async ({ page }, query) => {
  await page.getByTestId("search-input").fill(query);
  await page.getByTestId("search-submit").click();
});
Let the agents do this for you You rarely write steps by hand — /bdd-pipeline --gen scaffolds the feature and stubs, then the explorer fills the steps in against your live app. This section is the manual equivalent for when you want it.

The step-docstring convention

Every Given/When/Then needs a JSDoc block with four tags. It powers two things: the browsable step wiki and the lint gate that keeps the wiki accurate.

  • @domain — the area this step belongs to (non-empty).
  • @description — what the step does (non-empty).
  • @prereq — required state before the step runs (none is allowed).
  • @uses — fixtures/resources it touches, comma-separated (none is allowed).
$ npm run wiki         # regenerate the catalogue under docs/
$ npm run lint:steps   # fail if any step lacks a compliant docstring

lint:steps runs in the husky pre-commit hook, so a step without a docstring can't be committed.

The Playwright config

The scaffold ships two normal projects plus an agent-only runner. baseURL comes from TARGET_URL, so steps navigate with relative paths.

// playwright.config.ts (excerpt)
const targets = [
  { name: "desktop", device: "Desktop Chrome", use: { launchOptions: { slowMo: 1500 } } },
  { name: "mobile", device: "Pixel 7" },
];

use: { baseURL: required("TARGET_URL"), trace: "on", screenshot: "only-on-failure" }
  • Add or remove devices by editing the targets array — any Playwright device works.
  • Scenarios opt in via tags: a @desktop scenario runs in the desktop project, etc.
  • The agent-session project only exists when AGENT_SESSION is set, and globs only that ephemeral session's folder — your real projects and CI never see it. See Architecture → runner isolation.

Environment & credentials

Anything environment-specific — the target URL, credentials, feature flags — lives in .env (and CI secrets), never in a .feature file. Hardcoding a password into a scenario is an antipattern: it leaks secrets into version control and couples the test to one environment.

Never hardcode credentials in features When I sign in as "admin" / "hunter2" is wrong. Read creds from the world fixture, which sources them from the environment.

The world fixture exposes creds pulled from env, so steps stay declarative:

// tests/baseTest.ts (world fixture)
world: async ({}, use) => {
  await use({
    baseUrl: "",
    creds: {
      user: process.env.STANDARD_USER ?? "",
      pass: process.env.STANDARD_PASS ?? "",
    },
  });
}
// a step that reads creds from the world — no literals in the feature
When("I sign in with the standard user credentials", async ({ page, world }) => {
  await page.getByTestId("login-username").fill(world.creds.user);
  await page.getByTestId("login-password").fill(world.creds.pass);
  await page.getByTestId("login-submit").click();
});

Why not bake HTTP basic auth into the template? Because most apps under test don't use it — form login, OAuth, and SSO are far more common. Keeping the template auth-agnostic (creds via env, you write the sign-in step your app needs) stays reusable across all of them.
