why "actually works"

Most agentic test bots write tests that lie

They guess selectors from stale snapshots, then weaken assertions until the run goes green. playgentic is built to prevent exactly that.

Explores the live app

The bdd-explorer drives a real browser to locate elements — it never guesses selectors from stale artifacts. Every exploration is fresh.

An auditor fights back

A separate bdd-auditor adversarially reviews assertion strength and coverage — and can BLOCK weak tests before they ever reach your suite.

Heals without weakening

--heal repairs broken and flaky tests by re-exploring the live app — its explicit priority is not softening the assertion to make it pass.

Never touches prod

Agents work only inside an ephemeral .agent-sessions/ copy through an isolated runner. Your tests/ change only on an explicit promotion.

You hold the merge button

Nothing lands in your suite without a human gate — you review the auditor's verdict and the diff, then approve the promotion.

Real BDD, not throwaway scripts

Output is Gherkin .feature files + typed steps on Playwright + playwright-bdd — readable, reusable, and indexed in a self-generating step wiki.

What one command gives you

A batteries-included BDD suite, a self-indexing step catalogue, and the agent pipeline — wired together.

BDD suite

A playwright-bdd boiler with desktop/mobile projects, an example feature + step, a scenario-scoped world fixture, husky pre-commit, eslint & prettier.

Step wiki

npm run wiki parses the @domain/@description/@prereq/@uses docstring on every step into a browsable catalogue — so agents reuse steps instead of duplicating them.

Docstring lint

npm run lint:steps (in pre-commit) fails any commit where a step lacks a compliant docstring — so the wiki index never drifts from the suite.

Agent pipeline

Claude Code skills /bdd-pipeline --gen|--heal that scaffold work in isolation, drive the explorer, review with the auditor, and promote only on your approval.

/bdd-pipeline --gen | --heal

How the pipeline works

The orchestrator plans and scaffolds. One agent touches the browser. A second one tries to tear the work apart. You hold the merge button.

● Never touch prod Agents work only inside an ephemeral session copy; tests/ changes land only on promotion.
● One tool touches the browser Only bdd-explorer drives the playwright-test MCP — everyone else delegates.
● Adversarial review A separate bdd-auditor challenges assertion strength & coverage before promotion.
● Reuse before writing The orchestrator regenerates + reads the step wiki first, so new work reuses existing steps.
● Human gate at the end Nothing merges without you approving after review.
● Update agents in one place playgentic sync pulls the latest managed agents into every scaffolded project.

Get started

Scaffold a fresh suite, point it at your app, and run the example scenario. Full walkthrough in the docs.

  1. Scaffold a suite

    Generates the suite in a new folder (or merges into an existing project's package.json).

    $ npx playgentic init my-suite
$ cd my-suite

  2. Point it at your app

    Set TARGET_URL (and optional creds) in .env, then install browsers.

    $ cp .env.example .env   # set TARGET_URL
$ npx playwright install

  3. Generate the wiki & run

    Build the step catalogue, then run the example scenario.

    $ npm run wiki
$ npm test

  4. Let the agents write coverage

    In Claude Code (with the playwright-test MCP), run the pipeline. Keep managed agents current with playgentic sync.

    > /bdd-pipeline --gen
$ npx playgentic sync   # pull latest agent defs
